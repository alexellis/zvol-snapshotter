# ZFS snapshotter performance spike

Measured 3 October 2026 against upstream revision `0b664bd` through Slicer's
public SDK. Experimental Slicer networking changes were held constant for
the before/after comparison below. Six sequential samples per cell; warm
images and caches. These are observations, not production guarantees.

Host: Ryzen AI9 HX370, NVMe, Linux 6.8.0-142, OpenZFS 2.2.2, and containerd
1.7.25. Firecracker 1.17.0, isolated networking, 2 vCPUs, and 1 GiB RAM.
Storage: 30 GiB zvols on a dedicated 64 GiB sparse-file ZFS pool backed by
ext4/NVMe. ZFS sync stayed standard. A native-disk pool was not tested.

| Image / operation | Upstream, agent ms | Batch + flush, agent ms |
| --- | ---: | ---: |
| Standard normal launch | 501 | 468 |
| Minimal normal launch | 458 | 435 |
| Standard cold fork | 429 | 465 |
| Minimal cold fork | 439 | 394 |

Values are medians. The gain is mixed: normal launches improved modestly;
the standard cold-fork median regressed. The JSON companion contains all
16 measured cells, including original-network and tighter-polling controls.
It is not evidence of a universal performance improvement.

## Correctness before speed

The original local snapshotter revision `32c34ca` failed two full
prepared-application cold-fork runs. Current upstream passed 36 children
across three profiles and two images. Batching labels alone then failed the
same application check. Adding a host-volume fsync before the ZFS snapshot
made both modified rounds pass all 12 cold children. Guest `sync` was also
used before stopping the source.

The child controls checked prepared workspace content, a fresh RAM marker,
a zero RAM counter, and a rebuilt 300,000-document index. This is consistent
with buffered host block-device writes needing a flush before ZFS captures
the backing blocks. More durability and failure-injection coverage is
needed before treating this spike as a production release.

`go test -race ./...` passes. A command-boundary test checks literal label
values and names that collapse to the same sanitised property. The final
collision handling is unit-tested; the LAN benchmarks used distinct label
names. No claim is made for hot ZFS forking: it is not implemented in this
Slicer spike.

All owned VMs, commits, daemons, the loopback pool, the pool file, and the
copied licence were removed. Host networking and the existing devmapper
snapshot inventory matched preflight after cleanup.
